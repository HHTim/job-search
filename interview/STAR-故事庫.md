### A1. 反組譯私有 .jar 整合私有 API（合作金庫）

**適合回答**：技術深度、無文件情境下的問題解決、風險意識

- **S**：合作金庫個人網銀要從 JSP/JSF 重構為前後端分離架構（Angular + Spring Boot），但行內有一批以私有 .jar 封裝的核心邏輯（負責存取客戶機敏資料、串接電文系統），沒有原始碼也沒有官方文件。
- **T**：要在不破壞既有商業邏輯、也拿不到原始碼的情況下，把這些私有 API 整合進新架構。
- **A**：反組譯 .jar 還原邏輯結構，追蹤方法簽章與內部呼叫關係，比對電文系統介面規格，拼湊出正確且安全的呼叫方式，封裝成新架構可用的 service 層。
- **R**：私有 API 成功整合進新架構，重構沒有中斷既有商業邏輯，也沒有造成機敏資料外洩風險。

**15 秒版**：「重構銀行網銀系統時，遇到一批沒有原始碼的私有 .jar，我反組譯還原邏輯後把它安全整合進新架構。」

### A3. 新舊站心跳機制解決跨站閒置登出（WMS 財富管理平台）

**適合回答**：技術巧思、相容性設計、對既有系統的尊重（不硬改舊系統）

- **S**：WMS 從 Struts2/Spring MVC/Vue 重構為 Angular/Spring Boot，但因業務考量新舊兩套系統必須並行兩年，且共用同一登入態。舊站用 Session 判斷閒置登出，新站改用 Redis Token，兩套閒置計時邏輯互不相通——使用者只要在新站操作，舊站 Session 會因沒有互動而逾時，導致被舊站登出、SSO 狀態不同步。
- **T**：在不改動舊站核心邏輯的前提下，讓使用者只操作新站也不會被舊站判定閒置。
- **A**：設計新站定期發送心跳（heartbeat）請求，觸發舊站既有的 keepalive endpoint，模擬「使用者仍在舊站活動」，讓舊站 Session 計時器持續被重置；同時用 Token + DB 白名單機制串接新舊站驗證邏輯，確保登入態一致。
- **R**：使用者不論操作新站或舊站都不會被無預警登出，兩年過渡期內新舊站並行零 session 衝突。（履歷上只留了「Token + DB 白名單機制」這個 SSO 主幹，心跳機制是這題可以額外展開的技術細節）

**15 秒版**：「新舊系統要並行兩年又要共用登入態，我讓新站定期發心跳去觸發舊站的 keepalive，模擬使用者還在舊站活動，解決了使用者被誤判閒置登出的問題。」

### B1. Stored Procedure 重構，處理時間降 95%（APInfo）

- **S**：APInfo 平台的批次讀檔、存庫、下檔作業原本要耗時 4–6 小時，觀察到系統有大量 I/O 處理瓶頸。
- **T**：找出效能瓶頸並重新設計資料處理架構。
- **A**：提出以 Stored Procedure 重構資料處理流程，減少應用層與資料庫間的來回 I/O。
- **R**：處理時間由 4–6 小時縮短至 10–20 分鐘，節省 95% 以上等待時間。

**15 秒版**：「我把一個要跑 4 到 6 小時的批次作業，重構成 Stored Procedure，縮短到 10 到 20 分鐘。」
