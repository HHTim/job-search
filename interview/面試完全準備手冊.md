# Part A. 口試題

## A1. 短網址服務的高併發設計

### Step 1. 先釐清需求（開口第一件事，展現 SA 思維）

讀寫比通常讀 >> 寫（100:1 以上），但以下三個問題**每一個都會影響架構決策**，必須先問：

| 問題 | 若「要」 → 影響什麼設計 | 若「不要」 |
|---|---|---|
| **自訂短碼？** | 需查重（DB or Redis SET），無法純靠 ID 生成，要額外 unique check | 直接把 ID 轉 Base62，流程最簡單 |
| **點擊統計？** | 不能同步寫 DB（高流量下會打爆），要非同步：Redis `INCR` → 批次落地 DB | 省掉這條鏈路 |
| **過期機制？** | 需 TTL 欄位 + 定時清理 Job，或 Redis TTL 自動過期 | 資料永久有效，不用清理 |

> 面試技巧：問完後自己給假設值，例如「我假設不自訂短碼、要點擊統計、過期 30 天，以此為前提設計」，然後繼續。

### Step 2. ID 產生策略（高併發核心瓶頸）

**為什麼 DB auto-increment 不行？**

```
高併發下 DB auto-increment 的問題：

Thread 1 ─┐
Thread 2 ─┼──► DB: INSERT 等回應 ──► 取得自增 ID
Thread 3 ─┘
Thread N ─┘

問題：
1. 每個 ID 都要 round-trip 到 DB       → latency 高
2. DB 變成 single point of bottleneck  → throughput 低
3. 分庫分表後 auto-increment 會重複    → 正確性破壞
```

---

#### 方案一：號段模式 / Segment Mode（推薦，規模中等場景）

**核心思想**：DB 不再「每次發一個號碼」，改成「一次批發一段給你，你在記憶體裡自己發」。

```
DB: leaf_alloc 表
┌─────────────┬──────────┬───────┐
│  biz_tag    │  max_id  │  step │
├─────────────┼──────────┼───────┤
│  url_short  │  3000    │  1000 │  ← 已發到 3000，每次批 1000 個
└─────────────┴──────────┴───────┘

App Server A                    App Server B
┌─────────────────┐             ┌─────────────────┐
│ 號段 [1001,2000) │             │ 號段 [2001,3000) │
│ 目前發到 1523    │             │ 目前發到 2187    │
│ AtomicLong      │             │ AtomicLong      │
│ .getAndIncrement│             │ .getAndIncrement│
└────────┬────────┘             └────────┬────────┘
         │ 號段用完才去 DB 拿下一段        │
         └────────────────────────────────┘
                        ▼
           UPDATE leaf_alloc
           SET max_id = max_id + step
           WHERE biz_tag = 'url_short'
           （樂觀鎖，同時只有一台搶到）
```

**雙 Buffer 優化（美團 Leaf 實作）**：
```
問題：號段用完瞬間所有 thread 都在等 DB → 短暫 spike

解法：
Buffer A [1001~2000]  ← 正在使用，用到 80% 時背景預載 Buffer B
Buffer B [2001~3000]  ← 準備好，A 用完瞬間無縫切換

效果：DB 存取完全在背景，使用端感受不到任何延遲
```

**號段模式特性**：
```
優點：DB 壓力極低（1000 ID 只需 1 次 DB 操作）、ID 趨勢遞增對 index 友好
缺點：ID 不連續（A 發 1~1000，B 發 1001~2000，交錯出現）
      機器重啟時未用完的號段會浪費
      強依賴 DB，DB 掛掉需 fallback
```

#### 方案二：Snowflake（推薦，超大規模 / 多機房場景）

**核心思想**：不依賴 DB，靠「時間 + 機器編號 + 序號」三維度，在記憶體中產生全域唯一 ID。

**64-bit 結構**：
```
 63      62                    22          12           0
  |       |                     |            |           |
  ▼       ▼                     ▼            ▼           ▼
┌───┬─────────────────────────┬────────────┬────────────┐
│ 0 │   41 bits（毫秒時間戳） │ 10 bits    │ 12 bits    │
│   │   相對於自訂 epoch      │ worker ID  │ sequence   │
└───┴─────────────────────────┴────────────┴────────────┘
  │            │                    │             │
  │            └── 可用約 69 年     │             └── 同毫秒內最多 4096 個
  │                                 └─────────────── 最多 1024 台機器
  └─ 符號位固定 0（保持正數）

每台機器每秒：4096 × 1000 = 400 萬個 ID
1000 台機器每秒：40 億個 ID  → 短網址場景完全夠用
```

**產生流程**：
```
呼叫 nextId()
      │
      ├─ currentMs == lastMs → sequence = (sequence+1) & 4095
      │                             │
      │                             └─ sequence 溢位(==0)? → 等到下一毫秒
      │
      ├─ currentMs > lastMs  → sequence = 0，更新 lastMs
      │
      └─ currentMs < lastMs  → 時鐘回撥！拋出 Exception（最大風險點）

ID = (timestamp << 22) | (workerId << 12) | sequence
```

**時鐘回撥問題**（面試加分）：
```
NTP 校時可能讓時間往回跳 → Snowflake 拒絕產生 ID

解法：
  1. 小幅回撥（< 5ms）→ 等待即可
  2. 大幅回撥 → 切換備用 workerId，讓序號空間不重疊
  3. 改用 ULIDv2 / UUID v7 等更現代方案
```

**Snowflake 特性**：
```
優點：完全去中心化不依賴 DB、效能極高（純記憶體微秒級）、ID 含時間可反解
缺點：依賴系統時鐘、需管理 workerId 分配（N 台機器 workerId 不能重複）
```

---

#### 兩者比較 + 短網址場景選哪個

```
                  號段模式              Snowflake
依賴              DB                   系統時鐘
實作複雜度        中（需雙Buffer）      中（需處理時鐘回撥）
效能              高（絕大多數無IO）    極高（純記憶體）
ID 遞增性         強趨勢遞增            弱趨勢遞增（毫秒內無序）
分散式友好        需DB協調              天生去中心化
```

- 規模中等（< 百萬 QPS）→ **號段模式**，簡單穩定，ID 遞增對 MySQL index 友好
- 超大規模、多機房 → **Snowflake** 或美團 Leaf-Snowflake 混合方案

> 口訣：「號段模式靠 DB 批發，Snowflake 靠時鐘自給自足。」

最後補一句 Base62 轉換：ID（數字）→ Base62（0-9a-zA-Z）→ 短碼，6位可表示約 568 億組合，夠用。

### Step 3. 高併發讀取（讀 >> 寫，這是重點）

```
使用者點擊短網址
      │
      ▼
  本地快取 (Caffeine)  ──── hit ────► redirect
      │ miss
      ▼
  Redis Cluster        ──── hit ────► redirect + 回填本地快取
      │ miss
      ▼
  DB（MySQL/PostgreSQL）────────────► redirect + 回填 Redis + 本地快取
```

- 熱門短網址 → CDN / Edge Cache 在最前面擋
- Bloom Filter 擋不存在的短碼 → 防快取穿透打爆 DB

### Step 4. 高併發寫入 + 點擊統計

```
產生短網址（寫入）：
Client → API Server → 取 ID（號段/Snowflake）
                    → 非同步 MQ（Kafka）→ Consumer 落地 DB
                    → 立即回應短碼給 Client（不等 DB）

點擊統計（如果有）：
每次 redirect → Redis INCR short:xxx:count（非同步，不阻塞 redirect）
                → 定時 Job 批次同步到 DB
```

### Step 5. 快取三大問題對策

| 問題 | 情境 | 對策 |
|---|---|---|
| 穿透（查不存在的key） | 惡意打不存在的短碼 | Bloom Filter、空值也快取（短TTL） |
| 擊穿（熱點key過期瞬間） | 爆紅連結到期 | 熱點key加分散式鎖 or 邏輯過期 |
| 雪崩（大量key同時過期） | 批次匯入的短碼同時到期 | TTL 加隨機值、多級快取兜底 |

> 加分句：「我會先用號段模式解決 ID 產生瓶頸，多層快取處理高讀取量，MQ 非同步寫入避免 DB 成為瓶頸，再搭配 Bloom Filter 和 Rate Limiting 做防護——這套思路跟我們在金融批次系統處理高流量 API 的經驗是一致的。」

## A2. 資料庫正規化：階段與優缺點

用同一個**訂單系統**貫穿所有範例，從違反到修正，看清楚每一步在解決什麼。

### 1NF — 原子性（Atomicity）

**規則**：每個欄位只能存一個值，不能存陣列或清單。

違反 1NF：

| order_id | customer | products |
|---|---|---|
| 1001 | Alice | 手機, 耳機, 充電器 |

`products` 存多值 → SQL `WHERE products = '手機'` 無法正確查詢，應用層要自己 split 字串。

修正：一行一個值，主鍵變複合主鍵 **(order_id, product)**。

| order_id | customer | product |
|---|---|---|
| 1001 | Alice | 手機 |
| 1001 | Alice | 耳機 |

---

### 2NF — 消除部分相依（Partial Dependency）

**規則**：符合 1NF，且非主鍵欄位必須完全依賴「整個複合主鍵」，不能只依賴其中一部分。

> **只有複合主鍵才可能違反 2NF。**

違反 2NF，主鍵：**(order_id, product_id)**：

| order_id | product_id | quantity | product_name | product_price |
|---|---|---|---|---|
| 1001 | P01 | 2 | 手機 | 25000 |
| 1002 | P01 | 1 | 手機 | 25000 |

```
quantity     → 依賴整個主鍵 (order_id, product_id)  ✓
product_name → 只依賴 product_id                     ✗ 部分相依
product_price→ 只依賴 product_id                     ✗ 部分相依
```

問題：手機漲價 → 要改所有含 P01 的 row，改漏一筆就資料不一致。

修正：拆成兩張表。

**order_items**（order_id, product_id → quantity）
**products**（product_id → product_name, product_price）

---

### 3NF — 消除遞移相依（Transitive Dependency）

**規則**：符合 2NF，且非主鍵欄位不能依賴「其他非主鍵欄位」。

違反 3NF，主鍵：**order_id**：

| order_id | customer_id | customer_name | customer_city | city_zip |
|---|---|---|---|---|
| 1001 | C01 | Alice | 台北 | 100 |
| 1002 | C01 | Alice | 台北 | 100 |

```
依賴鏈（遞移相依）：
order_id → customer_id → customer_name  ✗
order_id → customer_id → customer_city  ✗
order_id → customer_id → city_zip       ✗
```

問題（三大異常）：
- **更新異常**：Alice 搬家 → 要改所有 Alice 的訂單 row，改漏就不一致
- **刪除異常**：刪掉最後一筆 C02 訂單 → Bob 的資料整個消失
- **新增異常**：想新增一個城市 → 沒有訂單就無法新增

修正：拆成三張表。

**orders**（order_id → customer_id）
**customers**（customer_id → customer_name, city_id）
**cities**（city_id → city_name, zip）

---

### BCNF — 3NF 的加強版

**規則**：每個「決定因子」都必須是候選鍵。

> **3NF 已足夠大多數情況。BCNF 處理的是 3NF 涵蓋不到的特殊角落。**

違反 BCNF 的案例（大學排課）：

| student | subject | teacher |
|---|---|---|
| Alice | 資料庫 | 陳老師 |
| Bob | 資料庫 | 陳老師 |
| Bob | 演算法 | 王老師 |

業務規則：每位老師只教一個科目（`teacher → subject`），但 teacher 不是候選鍵（單獨無法決定整個 row）→ 違反 BCNF。

問題：陳老師改教「進階資料庫」→ 要改所有陳老師的 row，改漏就不一致。

修正：拆成 **student_teacher** + **teacher_subject** 兩張表。

---

### 何時正規化到哪個程度？

| 場景 | 建議 | 理由 |
|---|---|---|
| 一般 OLTP（訂單/交易） | **3NF** | 一致性夠，JOIN 可接受 |
| 金融核心系統（帳務/合規） | **3NF 嚴格執行** | 錯一筆代價高 |
| 複雜排課/多候選鍵系統 | **BCNF** | 3NF 涵蓋不到的角落 |
| OLAP / 報表 / BI | **適度反正規化** | 查詢速度 > 一致性 |
| 高讀取 API（商品/文章） | **加冗餘欄位** | JOIN 成為瓶頸時 |

嚴格執行（≥ 3NF）的場景：金融帳務、有稽核/法遵要求、多系統共用的 Master Data。

> 💬 面試一句話：「OLTP 正規化到 3NF 確保一致性避免異動異常；BCNF 只在有多組候選鍵且產生衝突時才需要；報表或高讀取 API 再依效能需求做適度反正規化——用儲存成本換查詢效能。」

## A3. 開發系統遇到的難題（STAR 法則）

挑 1-2 個講深。依你背景的候選題材：

**題材A：Nginx 多環境路由**（Instana EUM UAT/PROD）
- 情境：多環境共用前端資源，EUM監控請求需導向對應後端
- 難點：SRI hash 不匹配、DNS 解析陷阱
- 行動：`if ($host)` + 變數化 `proxy_pass` 動態路由
- 結果：環境隔離且不破壞前端資源完整性驗證

**題材B：Spring 交易自我調用失效**
- 情境：同Service內部方法互呼叫，`@Transactional` 失效
- 難點：Spring AOP self-invocation 不走 proxy
- 行動：拆分Service 或 `AopContext.currentProxy()`
- 結果：修正交易邊界，避免資料不一致

**題材C：JPA 複合主鍵選型**（@IdClass vs @EmbeddedId）

> 技巧：不只講bug，要講「怎麼分析根因、怎麼驗證、學到什麼」，結尾補「這經驗讓我後來在類似場景會提前注意XXX」。

1. **訪談收集**：釐清真正痛點而非使用者以為的解法（Want vs Need）；挖掘現況流程、限制條件（金融業常有法遵限制）

> 💬 加分句：「使用者常直接跟你要一個解法，但我會往回追問一層確認背後的商業目的，避免做出技術上沒問題、卻沒解決真正問題的東西。」

## A5. 多專案時程管理，不讓上線 delay

1. **事前規劃**：WBS拆解、估工時留20% buffer、識別關鍵路徑（Critical Path）
2. **優先序**：重要/緊急矩陣、與PM對齊商業優先度
3. **風險管理**：提前識別跨團隊依賴等風險點、設Milestone頻繁checkpoint
4. **溝通**：站會同步、及早暴露問題（Fail Fast）
5. **技術面**：CI/CD自動化（Docker/K8s pipeline）、模組化平行開發

> 💬 加分句：「我的原則是『問題往前暴露，不往後拖』——發現時程風險立刻量化影響、提出至少兩個方案讓主管決策，而不是deadline前一天才說做不完。」

## A6. PG 不同意 CR 方向怎麼處理

1. **先理解對方立場**：效能？可讀性？架構慣例？時程壓力？CR分歧多半是「權衡點不同」而非對錯
2. **回到目標本質**：用具體指標討論（複雜度、測試覆蓋率、擴充性），避免「我覺得/你覺得」
3. **資料佐證**：效能測試數據、過往case、best practice；也保持開放，對方更合理就調整
4. **共識機制**：僵持不下拉高一層由team lead/架構師仲裁，或依coding standard裁定，避免拖延交付
5. **事後**：結論寫入team guideline，避免重複爭議

> 💬 加分句：「CR的目的是讓code變好，不是爭輸贏。」

# Part B. 上機考演算法（中英對照）

## B1. unaffectedChar

### 📖 英文原文
> A company is transmitting its data to another server. To secure the data against malicious activity, they plan to **reverse the data before transmitting**. They want to know **the number of data characters that do not change position** even after the data stream is reversed.
>
> **Input**: a string `dataStream`, representing the data to be transmitted.
> **Output**: an integer representing the number of characters that do not change position after reversal. If no such character is found or the string is empty, print `0`.
> **Constraints**: `0 ≤ length of dataStream`. Case sensitive, English letters only.

### 🇹🇼 中文對照
> 公司要傳輸資料到另一台伺服器。為了資安，傳輸前會**先將資料反轉**。他們想知道**反轉後位置不變的字元有幾個**。
>
> **輸入**：字串 `dataStream`。**輸出**：反轉後位置不變的字元數；找不到或空字串則輸出 `0`。**限制**：大小寫視為不同字元。

📚 **關鍵單字**：`reverse` 反轉｜`data stream` 資料流｜`case sensitive` 區分大小寫｜`constraints` 限制條件｜`malicious activity` 惡意行為

### 思路
反轉後位置 `i` 的字元變成原本 `n-1-i` 的字元 → 數滿足 `s[i] == s[n-1-i]` 的位置即可。

驗證 `alphxxdida`（長度10）：i=0(a=a)✓、i=4(x=x)✓、i=5(x=x)✓、i=9(a=a)✓ → 輸出 **4** ✓

### 解答
```java
static int countUnaffected(String s) {
    if (s == null || s.isEmpty()) return 0;
    int count = 0, n = s.length();
    for (int i = 0; i < n; i++) {
        if (s.charAt(i) == s.charAt(n - 1 - i)) count++;
    }
    return count;
}
```
- 複雜度：時間 O(n)、空間 O(1)
- 追問：「可否只走一半？」→ 可以，`i < n/2` 每次 `+2`，奇數長度中間字元必不變再 `+1`。先寫直觀版再口頭提優化。

## B2. largestLand

### 📖 英文原文
> In a city there are N houses **lying in a straight line**. Each house has a **house number** and a **position** indicating its distance from the entry point. Noddy wants to find the houses **between which he can build the largest possible house**.
>
> **Input**: first line: `num` and `val` (val is always 2). Next N lines: house number `H_i` and position `P_i`.
> **Output**: two space-separated house numbers **in ascending order** between which the largest plot is available.
> **Constraints**: `2 ≤ num ≤ 10^6`, `1 ≤ H_i ≤ 100`, `0 ≤ P_i < 10^6`.
> **Note**: No two houses share the same position. **In case of multiple possibilities, print the one with the least distance from the reference point.**

### 🇹🇼 中文對照
> 城市裡有 N 間房子**排成一直線**，每間有**門牌號碼**與**距入口的位置**。找出**之間空地最大**的兩間房子。
>
> **輸出**：兩個門牌號碼，**升冪排列**。**注意**：位置不重複；**多組答案時，取離參考點（入口）最近的那組**。

📚 **關鍵單字**：`plot of land` 一塊地｜`in a straight line` 排成直線｜`ascending order` 升冪｜`reference point` 參考點｜`least distance` 最短距離｜`space-separated` 以空格分隔

### 思路
1. 依**位置**排序 → 最大空地必在相鄰兩房之間
2. 掃描相鄰 gap 找最大；平手時因已排序，**用 `>`（嚴格大於）自然保留位置最小（離入口最近）的組合**
3. 輸出門牌**升冪**

驗證：排序後 `(2,0),(3,7),(1,9),(5,15),(4,30)`，gaps = 7,2,6,15 → 最大15在門牌5和4之間 → 升冪輸出 **`4 5`** ✓

### 解答
```java
import java.io.*;
import java.util.*;

public class LargestLand {
    public static void main(String[] args) throws IOException {
        BufferedReader br = new BufferedReader(new InputStreamReader(System.in));
        StringTokenizer st = new StringTokenizer(br.readLine());
        int num = Integer.parseInt(st.nextToken());
        st.nextToken(); // val 恆為2，讀掉

        int[][] houses = new int[num][2]; // [houseNo, position]
        for (int i = 0; i < num; i++) {
            st = new StringTokenizer(br.readLine());
            houses[i][0] = Integer.parseInt(st.nextToken());
            houses[i][1] = Integer.parseInt(st.nextToken());
        }
        Arrays.sort(houses, Comparator.comparingInt(h -> h[1]));

        long maxGap = -1; int h1 = -1, h2 = -1;
        for (int i = 1; i < num; i++) {
            long gap = (long) houses[i][1] - houses[i - 1][1];
            if (gap > maxGap) {           // 嚴格大於 → 平手保留離入口近的
                maxGap = gap;
                h1 = houses[i - 1][0]; h2 = houses[i][0];
            }
        }
        System.out.println(Math.min(h1, h2) + " " + Math.max(h1, h2));
    }
}
```

### ⚠️ 三大陷阱
1. n 達 10^6 → **必用 `BufferedReader`**，`Scanner` 會 TLE
2. 平手規則：`>` 而非 `>=`
3. 輸出門牌**升冪**，跟位置順序無關（範例是 `4 5` 不是 `5 4`）

## B3. 字串反轉（String Reversal）

📚 **關鍵單字**：`reverse` 反轉｜`in-place` 原地操作｜`palindrome` 回文｜`two pointers` 雙指針

筆試常見的三種題型，從簡單到進階：

### 題型1：整個字串反轉（最基本）

```
Input:  "hello"
Output: "olleh"
```

```java
// 解法A：StringBuilder（面試首選，簡潔）
static String reverse(String s) {
    return new StringBuilder(s).reverse().toString();
}

// 解法B：雙指針 in-place（面試官更愛考這個，展現思維）
static String reverse(String s) {
    char[] arr = s.toCharArray();
    int left = 0, right = arr.length - 1;
    while (left < right) {
        char tmp = arr[left];
        arr[left] = arr[right];
        arr[right] = tmp;
        left++;
        right--;
    }
    return new String(arr);
}
```

```
雙指針過程：
h e l l o
↑       ↑   swap → o e l l h
  ↑   ↑     swap → o l l e h → 等等，再來
    ↑↑       left >= right → 停止

實際：
h e l l o
左=0 右=4  swap(h,o) → o e l l h
左=1 右=3  swap(e,l) → o l l e h
左=2 右=2  left==right → 停止
結果：olleh ✓
```

### 題型2：反轉字串中的單字（常見進階題）

```
Input:  "Hello World Java"
Output: "Java World Hello"
```

```java
static String reverseWords(String s) {
    String[] words = s.trim().split("\\s+");  // 處理多餘空格
    int left = 0, right = words.length - 1;
    while (left < right) {
        String tmp = words[left];
        words[left] = words[right];
        words[right] = tmp;
        left++;
        right--;
    }
    return String.join(" ", words);
}
```

### 題型3：判斷是否為回文（Palindrome）

```java
static boolean isPalindrome(String s) {
    int left = 0, right = s.length() - 1;
    while (left < right) {
        if (s.charAt(left) != s.charAt(right)) return false;
        left++;
        right--;
    }
    return true;
}
// 時間 O(n)，空間 O(1)
// 注意：與 B1 的 unaffectedChar 概念相同，都是雙指針比對
```

筆試常見三種題型：

### 題型1：FizzBuzz（最經典，99% 會考）

```
1到N，可被3整除印Fizz，可被5整除印Buzz，都可以印FizzBuzz，否則印數字
Input:  N=15
Output: 1 2 Fizz 4 Buzz Fizz 7 8 Fizz Buzz 11 Fizz 13 14 FizzBuzz
```

```java
static void fizzBuzz(int n) {
    for (int i = 1; i <= n; i++) {
        if (i % 15 == 0)      System.out.print("FizzBuzz");  // 先判斷15，避免3和5都進去

}
```

```java
static List<Integer> divisibleBy(int n, int k) {

    }

}
```

## C2. Thread-Safe Singleton

📖 *Design a thread-safe singleton pattern.*

面試手寫 **DCL**（展現對 volatile 的理解），口頭補另外兩種。

```java
public class Singleton {
    // volatile 防指令重排序：new 分三步 (1)配置記憶體 (2)初始化 (3)引用指向
    // 若重排成 1→3→2，另一thread可能拿到「非null但未初始化完成」的物件
    private static volatile Singleton instance;
    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                  // 第一檢查：避免每次進鎖
            synchronized (Singleton.class) {
                if (instance == null) {          // 第二檢查：避免重複建立
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**靜態內部類**（lazy+無鎖，JVM classloader 保證）：
```java
public class Singleton {
    private Singleton() {}
    private static class Holder { static final Singleton INSTANCE = new Singleton(); }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}
```

**枚舉**（Effective Java 推薦，防反射/反序列化攻擊）：

## C6. Checked vs Unchecked Exception

📖 *What is the difference between checked and unchecked exceptions? When should you use each?*
🇹🇼 *Checked 與 Unchecked Exception 的差異？各自何時使用？*

📚 **關鍵單字**：`checked exception` 受檢例外｜`unchecked exception` 非受檢例外｜`propagate` 傳播｜`caller` 呼叫端｜`recover` 恢復

### 核心差異

```
Exception 繼承樹：

Throwable
├── Error                    ← JVM 層級錯誤，不用處理（OutOfMemoryError）
└── Exception
    ├── RuntimeException     ← Unchecked：不強制處理
    │   ├── NullPointerException
    │   ├── IllegalArgumentException
    │   ├── IndexOutOfBoundsException
    │   └── ...
    └── 其他 Exception       ← Checked：編譯器強制 try-catch 或 throws 宣告
        ├── IOException
        ├── SQLException
        └── ...
```

| | Checked Exception | Unchecked Exception |
|---|---|---|
| **繼承自** | Exception（非 RuntimeException） | RuntimeException |
| **編譯器強制？** | ✅ 必須 try-catch 或 throws 宣告 | ❌ 不強制 |
| **語意** | 可預期、呼叫端有能力處理的錯誤 | 程式邏輯錯誤、不應該發生 |
| **常見例子** | IOException、SQLException、ParseException | NPE、IllegalArgumentException、ArrayIndexOutOfBoundsException |

### 什麼時候用 Checked？

```java
// 呼叫端可以做有意義的處理 → Checked
public class FileService {
    // 呼叫端知道「檔案可能不存在」，可以提示使用者或用備用路徑
    public String readFile(String path) throws IOException {
        return Files.readString(Path.of(path));
    }
}

// 呼叫端用法：
try {
    String content = fileService.readFile("/data/config.txt");
} catch (IOException e) {
    log.warn("設定檔不存在，使用預設值");
    return defaultConfig;
}
```

### 什麼時候用 Unchecked？

```java
// 程式邏輯錯誤，不應該發生，呼叫端無法有意義地處理 → Unchecked
public void transfer(BigDecimal amount) {
    if (amount == null || amount.compareTo(BigDecimal.ZERO) <= 0) {
        // 呼叫端傳了非法參數，這是 bug，不是可預期的狀況
        throw new IllegalArgumentException("轉帳金額必須大於零");
    }
    // ...
}
```

### 自訂 Exception 設計（面試常問）

```java
// 業務層用 Unchecked（不強迫 Service 到 Controller 全部加 throws）
public class InsufficientBalanceException extends RuntimeException {
```

## C7. SQL — GROUP BY + HAVING

📖 *Write SQL queries using GROUP BY and HAVING.*
🇹🇼 *撰寫使用 GROUP BY 與 HAVING 的 SQL 查詢。*

📚 **關鍵單字**：`aggregate function` 聚合函數｜`GROUP BY` 分組｜`HAVING` 過濾分組後結果｜`WHERE` 過濾原始資料列

### WHERE vs HAVING 的根本差異

```
執行順序：
FROM → WHERE（過濾原始列）→ GROUP BY（分組）→ HAVING（過濾分組結果）→ SELECT → ORDER BY

WHERE  = 分組「前」過濾，針對原始資料列，不能用聚合函數
HAVING = 分組「後」過濾，針對聚合結果，可以用 COUNT/SUM/AVG 等
```

### 範例資料：orders 表

| order_id | customer_id | amount | status |
|---|---|---|---|
| 1 | C01 | 1000 | PAID |
| 2 | C01 | 2000 | PAID |
| 3 | C02 | 500 | CANCELLED |
| 4 | C02 | 3000 | PAID |
| 5 | C03 | 800 | PAID |

### 常見題型

**題型1：找出下單超過 N 次的客戶**
```sql
SELECT customer_id, COUNT(*) AS order_count
FROM orders
GROUP BY customer_id
HAVING COUNT(*) > 1;

-- 結果：C01(2次), C02(2次)
```

**題型2：找出總消費金額超過門檻的客戶（只計算 PAID 的訂單）**
```sql
-- WHERE 先過濾狀態，HAVING 再過濾聚合結果
SELECT customer_id, SUM(amount) AS total
FROM orders
WHERE status = 'PAID'          -- 先排除 CANCELLED（分組前）
GROUP BY customer_id
HAVING SUM(amount) > 1000;    -- 再過濾總金額（分組後）

-- 結果：C01(3000), C02(3000)
```

**題型3：各狀態的訂單數與平均金額（報表型）**
```sql
SELECT
    status,
    COUNT(*)            AS order_count,
    AVG(amount)         AS avg_amount,
    SUM(amount)         AS total_amount
FROM orders
GROUP BY status
ORDER BY total_amount DESC;
```

**題型4：找出有重複資料的 key（資料清洗常用）**
```sql
-- 找出同一個 customer_id + amount 出現超過一次的（可能是重複下單）
SELECT customer_id, amount, COUNT(*) AS cnt
FROM orders
GROUP BY customer_id, amount
HAVING COUNT(*) > 1;
```

### 常見陷阱

```sql
-- ❌ 錯：WHERE 不能用聚合函數
SELECT customer_id FROM orders
WHERE COUNT(*) > 1              -- 語法錯誤！
GROUP BY customer_id;

-- ✅ 對：聚合條件放 HAVING
SELECT customer_id FROM orders
GROUP BY customer_id
HAVING COUNT(*) > 1;

-- ❌ 錯：SELECT 的欄位必須在 GROUP BY 或聚合函數裡
SELECT customer_id, amount      -- amount 沒有在 GROUP BY 也沒有聚合
FROM orders
GROUP BY customer_id;           -- DB 不知道要顯示哪個 amount

-- ✅ 對：
SELECT customer_id, MAX(amount)
FROM orders
GROUP BY customer_id;
```

# Part D. Memory Cache 與鎖

> 上機考明確提示方向：用 Map 裝 DB 資料，判斷哪邊要上鎖。

## D1. 基本實作（首選）

```java
public class MemoryCache<K, V> {
    private final ConcurrentHashMap<K, V> cache = new ConcurrentHashMap<>();
    private final Function<K, V> dbLoader;

    public MemoryCache(Function<K, V> dbLoader) { this.dbLoader = dbLoader; }

    // computeIfAbsent 保證同key載入是原子的：
    // 多thread同時miss同一key時，只有一個會去查DB
    public V get(K key) { return cache.computeIfAbsent(key, dbLoader); }

    public void invalidate(K key) { cache.remove(key); }
}
```

## D2. 必考問答：哪邊要鎖、哪邊不用？

| 操作 | 要鎖？ | 原因 / 正確做法 |
|---|---|---|
| 單純 `get` 讀取 | ❌ | CHM 讀取無鎖（volatile 語意保證可見性） |
| `put` 單一寫入 | ❌ | CHM 內部保證單操作原子性（JDK8: CAS + synchronized bucket） |
| **check-then-act** | ⚠️ | `containsKey` + `put` 兩步會被插隊 → 用原子的 `putIfAbsent` / `computeIfAbsent` |
| **read-modify-write**（如累加） | ⚠️ | 用 `compute()` / `merge()` |
| **跨多 key 複合操作** | ✅ | CHM 只保證單 key 原子性 → `ReentrantReadWriteLock` 包整段 |
| 全量 reload | ✅ 或引用替換 | 最優雅：新 Map 裝好後 `volatile` 引用一次性替換，讀取端全程無鎖 |

## D3. 經典錯誤（面試官愛問你錯在哪）

```java
// ❌ 即使用 ConcurrentHashMap 仍有 race condition
if (!cache.containsKey(key)) {   // thread A、B 同時通過檢查
    V value = loadFromDb(key);    // 兩個都查了DB（快取擊穿）
    cache.put(key, value);        // 後寫覆蓋先寫
}
// ✅ 正確
cache.computeIfAbsent(key, k -> loadFromDb(k));
```

## D4. 讀寫鎖版本（若被要求不能用 CHM）

```java
public class RwLockCache<K, V> {
    private final Map<K, V> map = new HashMap<>();
    private final ReadWriteLock lock = new ReentrantReadWriteLock();

    public V get(K key) {
        lock.readLock().lock();           // 讀鎖：多讀並行
        try { return map.get(key); }
        finally { lock.readLock().unlock(); }
    }
    public void put(K key, V value) {
        lock.writeLock().lock();          // 寫鎖：獨占
        try { map.put(key, value); }
        finally { lock.writeLock().unlock(); }
    }
}
```

> 💬 口頭補充：「讀寫鎖適合讀多寫少，讀極多可升級 `StampedLock` 樂觀讀。實務上優先用 CHM 或 Caffeine，不重造輪子。」

# Part E. 分散式情境題

## E1. 多機器讀 DB + 本地快取，如何保證一致性？

**先講結論**：「本地快取的分散式一致性沒有完美解，只有取捨——看業務容忍多久的不一致窗口。」

由弱到強：
1. **TTL 過期**：短TTL（30秒~5分鐘）容忍短暫不一致 → 參數設定類資料
2. **Pub/Sub 廣播失效（最常用）**：更新時發失效訊息（Redis Pub/Sub、Kafka），各機刪本地快取，下次讀取回源。注意 Redis Pub/Sub 不保證送達 → 搭配 TTL 兜底
3. **兩級快取**：L1 本地（Caffeine 極短TTL）+ L2 Redis（單一事實來源）；更新：改DB → 刪Redis → 廣播刪L1
4. **版本號比對**：讀取先比對輕量版本號（Redis），不一致才重載

> 💬 金融加分句：「我會先問這份資料的一致性等級——餘額這種強一致需求根本不該用本地快取，直接查DB或Redis單一來源；本地快取只留給參數檔這類低敏感度資料。」

## E2. 多機器排程處理資料，如何防止重複處理？

**方案A：分散式鎖（搶主執行，其他機器 skip）**
- Redis：`SET lockKey machineId NX PX 30000`
  - `NX` 原子搶鎖、`PX` 過期防死鎖（機器掛掉自動釋放）
  - 釋放用 Lua 腳本驗證是自己的鎖才刪（防誤刪）
  - 進階：Redisson watchdog 自動續期（解決任務沒跑完鎖先過期）
- DB：悲觀鎖 `SELECT ... FOR UPDATE`；樂觀鎖 `UPDATE ... WHERE version=?` 成功者得標
- 現成框架：**ShedLock**（`@SchedulerLock` 註解，Spring 排程標準解）、Quartz cluster 模式

**方案B：任務分片（大家都做事，各做各的）**
- 靜態：`id % 機器數` 取模分配
- 動態框架：ElasticJob、XXL-JOB（自動感知節點增減重新分片）
- 適合資料量大到單機吃不下

**方案C：DB 搶單（狀態機）**
```sql
UPDATE task SET status='PROCESSING', owner=:machineId
WHERE status='PENDING' AND id IN (...)
-- 各機器只處理自己搶到的（affected rows）
```
- 更優雅：`SELECT ... FOR UPDATE SKIP LOCKED`（Oracle/PG）各機跳過已鎖的行，天然不重複
- 💡 **你的優勢**：「我們 Oracle 環境的批次處理就適合用 SKIP LOCKED 讓多節點並行搶單」

**🏆 滿分收尾（不管用哪招都要補）**：
> 「除了防重機制，我一定讓**處理邏輯本身具備冪等性**——唯一鍵防重複寫入、狀態機控制流轉、處理前檢查標記。因為分散式環境鎖可能失效（時鐘漂移、GC暫停導致鎖過期），**防重靠鎖，兜底靠冪等**。」

## E3. 大量資料處理經驗（主打 Spring Batch）

- **chunk-oriented processing**：分批讀-處理-寫，控制記憶體
- Reader 選型：`JdbcCursorItemReader`（省記憶體佔連線）vs `JpaPagingItemReader`（適合可重啟）
- 容錯：skip / retry / restart 機制
- 平行化：multi-threaded step、**partitioning**（呼應 E2 分片概念）
- DB 層：JDBC batch insert、深翻頁改 keyset pagination（游標式分頁）

## 10 題預測追問

1. `ConcurrentHashMap` JDK7 vs JDK8？→ 分段鎖 Segment → CAS + synchronized bucket + 紅黑樹

3. `ThreadPoolExecutor` 七大參數與提交流程？→ core → queue → max → reject（4種拒絕策略）
4. 快取穿透/擊穿/雪崩怎麼解？→ 見 A1 表格
5. Redis 分散式鎖的缺陷？→ 鎖過期與任務時長不匹配、主從切換鎖遺失（Redlock 爭議）
6. 樂觀鎖 vs 悲觀鎖場景？→ 衝突少用樂觀（version欄位）、衝突多/長事務用悲觀

9. `HashMap` 多執行緒會怎樣？→ JDK7 成環死循環、JDK8 資料遺失
10. 排程跑一半機器掛了？→ 鎖過期自動釋放 + 任務狀態表 + 冪等重跑
