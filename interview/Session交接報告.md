> 本報告目的：讓本地 Claude Code 完整承接這次對話的上下文、決策脈絡與未完成事項，不需使用者重新解釋背景。
> 搭配檔案：`面試完全準備手冊.md`（實際的面試內容/技術詳解，本報告是這份手冊的「產出紀錄與脈絡」）

## 一、專案背景與使用者需求

### 起因
使用者的朋友要面試一間 **SI（系統整合）/ 顧問公司** 的職缺，職務性質是 **SA + PG + 講師** 複合角色。使用者自己也想應徵同一間公司，因此拿朋友透露的面試題目，請 Claude 協助整理、補充相關考點、準備面試。

### 使用者背景（影響整份手冊的技術深度與舉例方向）
- 後端工程師，主力 Java / Spring Boot，2023/07 起累積經驗
- 目前任職金融業（銀行相關），職涯目標轉往科技廠 MES 工程師方向
- 技術棧：Java、Spring Boot、PostgreSQL、AWS（持有 CLF、AIF 證照）
- 弱項：前端，需求較細的拆解與範例
- 學習中：Docker、Claude Code、Git workflow + CI/CD、英文、AWS SAA
- 偏好：圖像/圖解記憶、繁中+English並行、避免無意義emoji、重視token效率、不熟悉詞彙先搜尋不憑印象

### 溝通與輸出偏好（本次對話中觀察到的具體要求）
1. 內容要整合成單一檔案，不要分散成多份（使用者明確反饋「分成兩份不好閱讀」）
2. 格式選擇 Markdown 優於 HTML（token 效率、可維護性考量後我方建議並獲採用）
3. 上機考的英文題目要「中英文對照」，使用者想順便練英文
4. 手冊要「隨時更新」——每次有新的面試資訊進來，都要直接改寫進同一份手冊，而不是另開新檔
5. 對於「只給結論沒解釋」的內容會追問到底（例如號段模式、Snowflake、Base62、TTL 都是使用者主動追問才補上的詳解）

### 階段5：追問基礎概念（第5輪對話，未進手冊，純問答）
使用者追問「什麼是TTL？為何要把ID轉Base62？」

**我的回答內容**（此輪對話內容目前**尚未寫入手冊**，屬於待辦事項）：
- TTL：Redis/Cache的存活時間機制，用SET...EX語法舉例，搭配時間軸圖解
- Base62：說明為何選62而非64（Base64的`+`和`/`在URL中有特殊意義）、進位制換算範例（125000000000 → "2CbnkCU"的完整除法過程）、字元對照表（0-9→'0'-'9', 10-35→'a'-'z', 36-61→'A'-'Z'）、不同位數可表示的組合數對照表
